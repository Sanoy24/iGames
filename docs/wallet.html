Wallet & Ledger System

Ledger-first financial core — every balance change is an immutable, auditable event.

Core Principle

🔒
Iron Rule: The wallet balance is never modified without creating a corresponding immutable ledger entry. Both operations always occur within the same MongoDB transaction. No exceptions.

Wallet Schema

FieldTypeDescription
userIdObjectIdOwner of the wallet

Each user gets one default CREDIT wallet, created automatically during first login.

Mutation Flow

Every debit or credit goes through mutateWalletInSession():

  1. Validate amount — must be a positive safe integer.
  2. Hash the request — SHA-256 of all request parameters for idempotency verification.
  3. Check idempotency — look up existing record by key + userId + action. If found and completed, return the cached result. If found and pending, throw ConflictException.
  4. Create pending idempotency record — marks the operation as in-progress.
  5. Load wallet — find the wallet document within the transaction session.
  6. Balance check (debits only) — ensure availableMinor >= amountMinor. Throw ConflictException if insufficient.
  7. Update balance — add (credit) or subtract (debit) the amount.
  8. Create ledger entry — the immutable record of this mutation.
  9. Complete idempotency record — store the result for future replay.

Two Calling Patterns

MethodUse Case
debit() / credit()Standalone operations (e.g., manual admin adjustment). Creates its own MongoDB session & transaction.
debitInSession() / creditInSession()Part of a larger transaction (e.g., ticket purchase, settlement). Joins the caller's existing session.

Game modules always use the InSession variants so that ticket creation + wallet debit + ledger write are atomic.

Idempotency System

The idempotency layer prevents double-charging and double-crediting:

  • Each operation has a unique idempotencyKey (e.g., keno-ticket:abc123).
  • The key is scoped to userId + action to prevent cross-user collisions.
  • A SHA-256 requestHash ensures replayed requests have identical parameters — if the hash differs, the system rejects the replay as a conflict.
  • Idempotency records have three states: pending → completed (or abandoned on transaction rollback).
