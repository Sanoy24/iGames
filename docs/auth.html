Authentication & Users

Telegram Mini App login → internal user mapping → first-party JWT sessions.

Identity Model

The system separates external identity providers from internal iGames users:

  • A User is an internal iGames account with a unique _id, displayName, and roles[] array.
  • An AuthIdentity links a provider (e.g., telegram) and a provider-specific user ID to an internal User.
  • One user can have multiple auth identities (Telegram today, email/password in the future).
💡
Telegram is just one login provider. The core backend never requires Telegram — game, wallet, ledger, and RNG modules have zero Telegram imports.

Step-by-Step

  1. Client sends raw initData — the URL-encoded string from Telegram.WebApp.initData is sent to POST /auth/telegram/miniapp.
  2. HMAC validation — the backend derives a secret key using HMAC-SHA256("WebAppData", BOT_TOKEN), then computes HMAC-SHA256(secret, data_check_string) and compares it against the received hash using timing-safe comparison.
  3. Freshness check — the auth_date timestamp is validated to reject stale initData.
  4. User resolution — UsersService.findOrCreateTelegramUser() looks up an AuthIdentity by provider=telegram + providerUserId. If none exists, it creates a new User and AuthIdentity in the same transaction.
  5. Wallet provisioning — WalletService.ensureDefaultWallet() creates a CREDIT wallet if the user doesn't have one yet.
  6. Token issuance — the system generates a JWT access token + a JWT refresh token, stores a RefreshSession document with the hashed refresh token, and returns both tokens to the client.

Token Payload

{
  "sub": "user_object_id",    // Internal iGames user ID
  "roles": ["player"],        // User roles
  "sessionId": "uuid-v4",     // Links to RefreshSession document
  "iat": 1715600000,
  "exp": 1715600900
}

Refresh Flow

  1. Client sends the refresh token to POST /auth/refresh.
  2. Backend verifies the JWT signature using JWT_REFRESH_SECRET.
  3. Looks up the RefreshSession by sessionId from the payload.
  4. Verifies the session is not revoked and not expired.
  5. Performs a timing-safe comparison of SHA-256(refreshToken) against the stored hash.
  6. Revokes the old session, creates a new one, and returns a fresh token pair.
🔒
Security: Refresh tokens are never stored in plaintext. Only a SHA-256 hash is persisted. Token comparison uses crypto.timingSafeEqual() to prevent timing attacks.

Roles & Guards

The system uses NestJS guards for route protection:

  • JwtAuthGuard — validates the Bearer access token and injects the user into the request.
  • RolesGuard — checks the user's roles[] array against required roles on the route.

Default roles: player (assigned on registration), admin (manually assigned or via dev seed).

Dev Seed (Non-Production)

When NODE_ENV !== 'production', a dev endpoint allows creating seeded admin users for testing:

POST /auth/dev/seed
{ "displayName": "Test Admin", "roles": ["player", "admin"] }

This creates (or reuses) a user and returns a valid token pair. This endpoint is disabled in production.
